# 从 OCR jsonl 提取列名的 LLM 组件 —— 设计规格

状态：**待审阅**。本文件经设计对话逐节确认后写成；批准后才进入实施计划。

---

## 1. 这个组件做什么

读入一份 jsonl（每条记录 = 一个「文件 + 工作表」），用 LLM 判断每张表的
**标题行区**，产出**列名**，写出**两份产物**：一份 jsonl 给机器，一份 md 给人。

**一句话**：伙伴的代码负责**框范围**和**全量读取**；本组件负责**判定标题行区**。

## 2. 明确不在范围内

- **下游怎么消费这份 jsonl** —— 会有下一步动作，本组件只负责写出来。
- **OCR 本身** —— 另一条链路，会处理 PDF 等我们读不了的形式。**它不会被取消。**
- **伙伴的标题行区判定** —— 它不做这件事，这正是本组件存在的理由。
- **与 `excel-to-md` 的运行时耦合** —— 两边只共享数据格式，不共享代码、不互相调用。

## 3. 术语：以 `excel-to-md/GLOSSARY.md` 为唯一权威

`excel-to-md` 的 `AGENTS.md` 声明 `GLOSSARY.md` 是术语的唯一权威。核对结果：

| 权威词 | 含义 | **明令避免** |
|---|---|---|
| **标题行区** | 一个表顶部被判定为表头的**连续行块**，可以为 0 行，**用起止行号表示，不用布尔值** | ~~表头~~、~~列名行~~、~~标题~~ |
| **数据区** | 标题行区以下 | ~~内容区~~、~~正文~~、~~表体~~ |
| **表范围** | A1 记法的矩形，如 `A3:C42` | ~~边界~~、~~尺寸~~、~~区域~~ |

**硬要求：不得使用「表头」「标题」这两个词。**

- **「列名行」有一个被严格限制的例外**：提示词为了可读性可以使用它，但**必须同时给出权威
  表述「标题行区的最下面一行」**（见 §7.1）。代码、产物与本文档一律不用它。
- 「输出的列名取哪一行」在这套权威词汇里原本**没有独立术语**：它就是**标题行区的最下面一行**。
- 模型不认识「标题行区」这个生造词，**提示词必须当场给一句可判定的定义**，而不是只给名字。
- `header_rows` 用**起止行号**而不是布尔值，与 `excel-to-md` 的 sidecar 一致。

## 4. 职责边界

| 谁 | 做什么 |
|---|---|
| **伙伴的代码** | 框定**表范围** + **全量读取**每列的单元格内容。**不判标题行区** |
| **本组件的代码** | 读 jsonl → 渲染提示词 → 调用模型 → **兜底解析** → **结构校验** → 汇总写 jsonl + 渲染 md |
| **模型** | **判定标题行区**（存在与否、起止行号），并对每列产出**路径**；给出 `reason` |

**代码不推导、不补写列名。** 列名由模型产出（这是刻意的取舍，见 §11）。

## 5. 输入契约

### 5.1 字段：**按「字段不定的袋子」处理**

输入记录的字段名**不确定**（伙伴的契约未冻结）。因此：

- 找出**长文本字段**当作正文（若有）
- 找出**能识别成表范围与单元格内容**的字段当作数据来源
- **认不出来就明确报错**，不猜、不静默跳过

> **为什么这么设计**：前几轮我两次假设了输入形状、两次都错。把「字段未知」当成设计前提，
> 不管伙伴最后给什么字段，代码都不用改。

### 5.2 每个表需要拿到的东西

- **表范围**（A1 记法，如 `A2:C6`）
- **每列的单元格内容**，按行序（自上而下）

按列组织 ⇒ 每一列的标题行区单元格在**该列最前面、天然连续**，不需要把 jsonl 重建成网格。

## 6. 模型输出契约

```json
{
  "header_rows": [2, 3],
  "columns": ["2024 年度 / Q1", "2024 年度 / Q2"],
  "reason": "第 2 行是分组表头（2024 年度 横跨 Q1/Q2），第 3 行是列名行；第 1 行「季度销售报告 2024」横跨整表宽度，是标题行，排除"
}
```

```json
{
  "header_rows": null,
  "columns": [],
  "reason": "第 1 行就是数据（100/200/300），本表没有标题行区"
}
```

- `header_rows`：**表内 1-based 起止行号**的二元组，或 `null`（= 0 行）
- `columns`：**路径**的字符串数组，各层用 `" / "` 拼接，从最上层到**标题行区的最下面一行**。单层时即该值本身
- `reason`：**必填**。是审计线索，不是装饰 —— 本地部署没有 tracing，一批结果不对时，
  `reason` 是判断「提示词理解错了」还是「模型顺从了错误的表范围」的唯一依据

### 6.1 代码的校验（只查结构，不查内容）

| 检查 | 违反时 |
|---|---|
| `header_rows` 是 `null`，或连续区间 `[a,b]` 且 `1 ≤ a ≤ b ≤ 表行数` | 带具体错误**重问一次**（有界）；仍失败 ⇒ 该表**标记失败，不写列名** |
| `header_rows: null` 必须配 `columns: []`（自洽性） | 同上 |
| `columns` 是数组，每项是**非空字符串** | 同上 |
| **列数 == 该表在 jsonl 里的列数** | 同上。这是唯一能与源对齐的硬检查，能抓到漏列/多列 |

**绝不静默接受。** 也**绝不因为校验失败就输出一份看起来合格的列名** ——
宁可报「这张表我没判出来」。

## 7. 提示词设计

### 7.1 术语定义（提示词内当场给出，可判定而非形容词）

| 词 | 提示词里的定义 |
|---|---|
| **标题行** | 只出现一次、横跨整表宽度、描述整张表的文字（如 `季度销售报告 2024`）。**不属于标题行区，要排除** |
| **标题行区** | 描述各列含义、位于数据之上的**连续行块**（一行或多行） |
| **列名行** | 标题行区里**最下面**那一行。**`columns` 的取值来自它**，`path` 来自标题行区各层 |
| **分组表头** | 标题行区里列名行之上的行（如 `2024 年度` 横跨 Q1/Q2）。**拼进 `path`** |

> 提示词内为可读性可以使用「列名行」「分组表头」作为**局部说明**，但**必须同时给出
> 「标题行区的最下面一行」这个权威表述**，避免词义漂移。

### 7.2 硬约束（写进提示词原文）

```
- 只输出 JSON，不要解释、不要 markdown 围栏
- columns 的每一项是「路径」：标题行区各层用 " / " 拼起来，从最上层到列名行
- 单层标题行区时，路径就是那个值本身
- 路径里的每一段必须照抄原文的单元格：不许改写、翻译、补全、纠错、去空格
- 空单元格跳过，不拼进路径
- 如果这张表没有标题行区（第一行就是数据），输出 {"header_rows": null, "columns": [], "reason": "..."}
- 必须给出 reason
```

**「照抄原文」是防幻觉的主力**：它把模型的角色从「写列名」压回「抄列名」。

### 7.3 必须给「没有标题行区」这条路

**这是全篇最重要的一条。** 如果提示词不通向这个答案，**模型在不确定时唯一的出路就是编一份出来**。

必须**既给规则、又给负例**：本地弱模型对「示范」的模仿强于对「规则」的服从，
只给正例会让它归纳出「总该有标题行区」。

### 7.4 few-shot：四个例子

1. 单层标题行区 ⇒ `["产品", "数量", "单价"]`
2. 两层 + 分组表头 ⇒ `["2024 年度 / Q1", "2024 年度 / Q2"]`（含**横幅重复取值**的样子）
3. **标题行 + 列名行** ⇒ 证明标题行被排除（最容易错的一例）
4. **没有标题行区** ⇒ `{"header_rows": null, "columns": [], "reason": "..."}`

### 7.5 不给模型的东西

- **不给 md** —— md 是给人的那份
- **不给本组件的任何推断或候选**（不给「标题行区可能是第 2 行」这类提示），避免它顺从我们的错误
- **不给伙伴的其它字段**（表范围除外，因为范围定义了「这张表」）

## 8. 运行形态与配置

```
python -m llm_column_extract <input.jsonl> [-o <dir>]
```

- 逐**记录** → 逐**表** → 每表一次调用
- 产物两份：`<name>.out.jsonl`（机器）+ `<name>.out.md`（人）
- **md 由代码从 jsonl 渲染**，不由模型生成 ⇒ 两份不可能互相矛盾，且解析失败不会连带毁掉 md
- **配置项**：模型名、`base_url`、密钥、超时、重试上限、提示词版本

**不得依赖网关的结构化输出能力**（`response_format`）。它支持就是可选加速；
**无论如何代码侧都要有兜底解析**（剥 markdown 围栏、容忍前后杂字、JSON 坏了要报错而不是猜）。
换模型、换网关都不需要改代码。

## 9. 错误处理

**逐表隔离必须一开始就做。** 刚做完的 `excel-to-md validate` 因为漏了这条，被独立审查
判成 Important：一张表炸掉整轮运行，健康的工作表连产物都没有。同样的坑不踩第二次。

| 情形 | 处理 |
|---|---|
| 单表调用失败（超时、网关 5xx） | **有界重试**；仍失败 ⇒ 该表标记失败，**继续下一张表** |
| 单表解析/校验失败 | **带具体错误重问一次**（有界）；仍失败 ⇒ 该表标记失败 |
| 单表失败 | **该记录照样写出来**，该表的 `columns` 缺失、带 `error` 文本 |
| 单记录失败 | **不中断整批** |
| 整批跑完 | **退出码非 0，但产物照写** |

最后一条与 `excel-to-md` 的取舍**刻意不同**（那边是「读不了就不写产物」）。理由是这里是
**批量**：跑 500 条，第 3 条坏了不该让你损失另外 497 条的结果。

**串行执行**，不做并发。顺序对排查更重要；等跑过真实批次、有实测数据之后再考虑是否开并发。

## 10. 测试策略

**关键决定：模型调用不进单元测试。**

| 测什么 | 怎么测 |
|---|---|
| 提示词渲染 | 纯函数：给定一张表 ⇒ 提示词字符串。断言术语没写错、行号从 1 起 |
| **解析 + 校验** | **测试主力**。纯函数，喂各种坏 JSON：围栏、截断、漏列、多列、`header_rows` 越界、自洽性违反 |
| md 渲染 | 纯函数，从 jsonl 渲染 |
| 整条流水线 | **假 client**（返回预置响应）⇒ 无网络、无模型也能测通，含全部失败路径 |
| 真实模型 | **不进单元测试**。它是外部依赖，会漂 |

**假 client 是本节的关键设计** —— 它让「逐表隔离」「有界重试」「部分成功」这些行为
**全部可测**，而且跑得飞快。

## 11. 产出契约（要写出来的东西）

### 11.1 jsonl（给机器）

```json
{
  "ID": "...",
  "FileName": "...",
  "sheet": "...",
  "tables": [
    { "range": "A2:C4", "columns": ["产品", "数量", "单价"] }
  ]
}
```

- **逐表**，不拍平。拍平形状在 `excel-to-md` 的验证器那边判 `partial`、覆盖率 0%；
  逐表能逐表核验 —— 而「表范围的框定」正是最想核验的东西
- **`columns` 的元素是路径**（全路径），不是最下层的短名。单层时两者相同
- 没有标题行区的表：`columns: []` —— **必须给空数组，不能省掉字段**（省掉会被判成格式错误）
- 诊断字段（模型名、提示词版本、重试次数、`reason`、`error`）**直接放在记录里**
- 别名兼容：`tables`/`Tables`、`range`/`Range`、`columns`/`列名`、`sheet`/`Sheet`

### 11.2 ⚠️ 硬约束：`columns` 的元素必须是**字符串**

`excel-to-md` 的 `load_claimed` 对 `columns` 的每一项执行 `str(entry)`。若写成
`{"name": "Q1", "path": "..."}` 对象，会被**字符串化成一坨** `"{'name': 'Q1', ...}"`
—— 列名全部错掉，**而且不会报错**（它只校验形状、不校验内容）。

### 11.3 md（给人）

由代码从 jsonl 渲染。

## 12. 已知取舍与未决项

### 12.1 已知取舍（明确接受，不是疏漏）

- **列名由模型写出 ⇒ 本组件无法自动判断某个列名是不是编的**（没有「原文里有没有这个词」
  这一步）。对真实 `.xlsx` 来源无所谓（`excel-to-md` 会拿真值核）；对 PDF 来源则失去这道
  防线。这是选择「纯提示词」的代价，已明确接受。
- **模块级术语妥协**：提示词为可读性使用「列名行」「分组表头」，而这两个词在
  `excel-to-md` 里是避免词。规避方式见 §7.1 的强制同时给出权威表述。

### 12.2 未决项（不阻塞实施，但迟早要定）

1. **伙伴 jsonl 的确切字段名** —— 目前按「字段不定的袋子」设计以规避。
2. **`header_rows` 的行号基准与伙伴是否一致**（表内 1-based vs 工作表绝对行号）。
   本设计假定**表内 1-based** 并在提示词里写明；若伙伴给的是绝对行号，需在渲染前换算。
3. **并发与成本的实测数据** —— 先串行，跑真实批次后再决定是否开并发。
4. **提示词的迭代机制**：提示词版本如何编号、如何在产物里留下版本号（§8 已列为配置项，
   具体形式待实施时定）。
